# Northframe audit and refinement, October 10, 2026

The application audit covers the marketing and concept pages, conversion flow, authentication, client and studio portals, payment lifecycle, database migrations, storage, notifications, realtime updates, motion, accessibility, configuration, dependencies and release processes. Improvements preserve the existing Glacier brand and pricing. This report distinguishes implemented fixes and local verification from live provider verification.

## Payment and database correctness

- Pending bank processing no longer invites another checkout. Payment return pages check the specific initial or final obligation, use a neutral confirmation title and show pending confirmation until the stored state changes.
- An uncertain saved-card charge keeps its processing claim. Reconciliation determines whether Stripe received it; a network error no longer silently releases the claim and invites a second charge.
- Webhook and reconciliation finalization validate currency and payment-stage metadata. Replaying an event repairs a ledger write that failed after the project was marked paid.
- Cumulative refunds are recorded in a PostgreSQL transaction under a project lock. Ledger, project totals, source payment status and timeline update together. Repeated or out-of-order totals cannot inflate refunds; an event-write failure rolls back the transaction. Open disputes retain their disputed state.
- Studio refunds check transactional storage before contacting Stripe, require confirmed success, and read Stripe's cumulative refunded amount. Pending automatic duplicate refunds are flagged for review rather than reported as completed.
- Approval and feedback submission share a project lock. Approval requires a paid project, a reviewable preview and no unfinished submitted feedback round. Only the winning approval initiates the final charge.
- Launch and completion require the initial payment and remaining balance to be settled. UI and server cancellation eligibility use the same published three-calendar-day rule and reject invalid/future timestamps.
- Reconciliation rotates through a separate checked-at table rather than repeatedly visiting only the newest projects. Old open projects with payment history remain eligible; failed attempts rotate too. An incomplete Stripe search cannot release an uncertain claim.
- Invoice references retain the complete payment UUID instead of a collision-prone six-character prefix. The format of rendered invoice numbers changes; payment IDs and payment history are unchanged. References wrap on phones.

Required migrations, in order after the existing migrations:

1. `supabase/migrations/20261010000000_atomic_refunds.sql`
2. `supabase/migrations/20261010010000_review_guard.sql`
3. `supabase/migrations/20261010020000_reconciliation_rotation.sql`

These migrations were executed against local PostgreSQL through PGlite, including rollback, role/column permissions, owner reads, approval/feedback ordering and reconciliation rotation tests. They were **not applied to the hosted Supabase database**. Refund storage, review approval and cron reconciliation fail closed if their required functions are missing. Apply the migrations before relying on those production flows. Also confirm the earlier profile-hardening migration is present.

## Authentication, inquiry and account protection

- Safe return paths reject control characters, backslashes, whitespace and host-changing URLs. Auth callback errors preserve the safe destination; proxy redirects retain refreshed auth cookies and private cache headers.
- Sign-out is local to the device and removes the application's Supabase session cookies, PKCE verifier and preview cookie even when the provider cannot complete sign-out. Cross-origin sign-out is refused.
- Auth and server-action controls use synchronous in-flight guards. Inputs lock during submission. Invalid auth fields receive keyboard focus and associated errors; names and email inputs have sensible length bounds.
- Admin client preview refuses all portal mutations at the server boundary, including profile/security and payment changes. Read-only account controls reflect that restriction.
- Inquiry drafts validate restored types, steps and submission IDs. Navigating away flushes the draft, while successful submission cannot restore an old draft. Duplicate submission lookup is scoped to the signed-in owner.
- Inquiry requests are bounded, validated and origin checked before storage. Authenticated account and IP rate limits reduce casual abuse. Development fixture mode refuses delivery before any database or email write.
- Webhook body reads and vendor-status responses have streaming byte limits. Missing Stripe signatures are rejected before SDK work. Supabase reads have timeouts.
- Account deletion checks database/storage failures and refuses truncated reads. It verifies and expires open checkout sessions first; completed-but-unrecorded sessions and provider outages block deletion. Actual deletion was not performed.
- Concurrent upload confirmation no longer deletes a file already claimed by another successful confirmation. File deletion checks storage failure before removing its database record.

## Dashboard and purchase clarity

- Database read failures reach the portal error boundary instead of producing reassuring empty lists. Projects, payment ledgers, milestones, unread counts, inboxes, files, feedback and notes use bounded pagination where complete sets are required.
- Active-project counts exclude unaccepted requests. Outstanding amounts include unpaid Launch totals, and project cards show unpaid totals or processing state. Payment summaries describe net paid amounts accurately.
- Revenue graphs support negative net-refund months. Monthly buckets use the same Chicago calendar as the rest of the portal.
- Requested feature, timeline and project-type IDs display their human-readable labels. Ready/completed/cancelled copy and inbox captions describe the actual workflow.
- Message threads follow new messages only when the reader is near the bottom. Sending handles IME composition, avoids duplicate submissions and preserves text entered during an outstanding send. Realtime refresh failures are handled.
- File upload controls are keyboard-operable buttons. Signed downloads navigate after the asynchronous URL request, avoiding popup blockers.
- Refund inputs validate a positive exact amount with at most two decimal places and enforce the selected payment's available amount. Confirmation shows the exact amount and original payment method.
- Shared native dialogs provide top-layer focus isolation, busy guards, backdrop/Escape handling and focus return after their exit. File/milestone deletion, approval, collection, refunds, feedback and Google disconnection use consistent confirmations.
- Marketing and portal 404 boundaries use their existing layout without duplicating navigation and footer. The internal design-system page is available in development and gated in production.

## Motion, responsive behavior and concepts

- A root motion provider covers every route, including concept lightboxes that previously could remain invisible. Interactive movement uses shared spring settings; CSS displacement uses a sampled damped spring with an easing fallback.
- Reduced long hero, section, navigation, progress, image hover and arrival timings. Progress animates transforms rather than layout width. Short opacity transitions accompany spring movement.
- Scroll reveals work for tall mobile sections. Reduced-motion, low-power, slow-network and offscreen guards remain in place. Decorative repeating motion and loading indicators retain their appropriate continuous behavior.
- Mobile navigation keeps scroll lock and background isolation through its exit, restores focus and handles a resize to desktop. Nested overlays use a shared reference-counted scroll lock.
- Lens lightbox uses a native dialog with keyboard navigation, swipe controls and focus return. Its booking form prevents native URL submission of contact fields and clearly reports local demo behavior. Booking anchors clear both sticky headers on phones.
- Portfolio image tracking uses motion values and springs, respects reduced motion and stays within the viewport. Work rows open accessible project details. The resume control links to the actual resume section; image alternatives and availability copy are accurate.
- Fictional portfolio and cafe contact controls now produce explicit demo feedback. Cafe calls to action say “Plan a visit”; no fictitious order/call/message is sent. Freelancer booking feedback clearly says nothing was added to a calendar.
- Organization day tabs remain three equal columns on small phones instead of an awkward two-plus-one wrap.
- Privacy copy accurately describes essential auth/preview cookies, browser-local drafts/theme, provider processing and retained payment/project history. Legal update date reflects this review.

## Verification and release process

- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run contrast` and `git diff --check` pass. The test suite has 17 files and 155 passing tests.
- `npm run check:copy` passes. `npm run check:seo` passes against the existing public deployment: robots and llms.txt are found and public content is open to the listed crawlers. This external scan does not verify the new deployment.
- Compatible Next.js and ESLint Next patch updates to 16.3.8; production dependency audit reports zero vulnerabilities. The full dependency audit still reports five high findings in the development-only braces/micromatch/glob chain. Its suggested force-fix would replace the compatible Next lint toolchain with an old major version and was not applied.
- Added GitHub Actions checks for lint, typecheck, tests, contrast, production dependency audit and build on main pushes and pull requests. Vitest uses an ESM configuration and PGlite runs the real migration files.
- Explicit build/tracing roots prevent unrelated parent lockfiles influencing this standalone app. Secrets, browser screenshots, generated build files and unrelated local files are excluded from the commit.

## Limits and production follow-through

1. Apply the three new migrations and confirm `CRON_SECRET` in the deployed environment. The local Supabase URL and cron secret are unset; hosted database migrations and deployed provider configuration could not be verified from this workspace.
2. Complete live/test-provider end-to-end authentication, email delivery, upload/download and Stripe lifecycle verification with an appropriate signed-in test account. Unit tests and local database tests do not prove live credentials, webhook delivery or simultaneous multi-session PostgreSQL concurrency.
3. Inquiry throttling remains best effort per serverless instance. Use a platform firewall/shared limiter if a guaranteed cross-instance limit becomes necessary. This audit does not claim durable throttling.
4. Account cleanup spans Auth, database and storage, so it remains a multi-service process rather than one transaction. Errors stop further cleanup; a partial failure may need studio recovery. Large list loads have an explicit 50,000-row limit, and conversations intentionally show the latest 1,000 messages.
5. Physical iPhone/Safari behavior, OS reduced-motion runtime behavior, assistive technology on real devices and production performance metrics remain unverified. Reduced-motion rules were inspected in source; desktop Chromium viewport checks cannot establish every device's behavior.

No audit can establish that a production system is “perfect.” The implemented fixes are locally verified; the outstanding items above describe the precise limits of that evidence.
